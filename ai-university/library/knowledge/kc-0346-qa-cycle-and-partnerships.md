# Delivery QA and building long-term partnerships

**What:** How to deliver so one project becomes many. Prototype fast to a working
version, then run a two-sided QA cycle: a week of internal QA (test on sample and
real data, stress edge cases, fix before the client sees anything) followed by a
week of client QA (they test in the real world and give feedback you iterate on).
Then treat every project as the start of a relationship, not a one-off.

**Why it matters:** QA protects you from edge-case failures and signals
professionalism, which builds the trust that turns a single build into ongoing
work. Long-term value comes from expansion and case studies, not from chasing new
logos each time.

**The moves:**
1. Prototype quickly to a live working version, then test — don't overthink the
   first pass.
2. Run internal QA (sample + real data, edge cases) before the client sees it.
3. Give the client a QA window to test in the real world and iterate on feedback.
4. Collect baseline data and results to build case studies proving ROI.
5. Expand: turn one project into several via demonstrated ROI, offer ongoing
   optimization, and build relationships with more than one person in the org.

**Watch out for:** Forgetting to collect baseline data means you can't build a
strong ROI case study afterward — capture it before you start. When you can show
"this saved you 10x what you paid," clients stop thinking about cost and ask what
else you can do.
