# Fitting model tier to task difficulty

**What:** A selection heuristic: rate the difficulty of the task, then choose the
cheapest model that clears that bar rather than defaulting to the most capable one.

**Why it matters:** Paying for a top-tier model on a routine task is wasted unit
economics. If a task is a "five" in difficulty, you generally need a five-or-six
model, not a ten. Matching tier to need is how you keep quality while controlling
spend at scale.

**The moves:**
1. Estimate how hard the task actually is and what quality bar counts as "good
   enough."
2. Reserve the most expensive/capable models for genuinely hard reasoning, judging,
   and strategy work.
3. Route routine, well-scoped, or high-volume tasks to cheaper models.
4. Re-check the fit periodically — model prices and capabilities shift.

**Watch out for:** Under-provisioning hurts on tasks that truly need frontier
reasoning; over-provisioning quietly drains budget on trivial ones. This is a
judgment call informed by testing, not a fixed rule.

**Original example to invent:** Frame the tier-to-task decision around a different
workload than the source's coding and API tasks.
