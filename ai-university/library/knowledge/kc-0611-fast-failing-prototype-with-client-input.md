# Get to a failing prototype fast, and lean on the client's expertise

**What:** Rather than going from discovery call to a perfect production system, race
to a rough prototype that will break. Each early failure surfaces edge cases you can
turn into guardrails. In parallel, tell the client upfront that you'll need their
subject-matter expertise, because you're building the system *for their* process.

**Why it matters:** Overthinking the first version is the main thing that stalls
builders. A prototype that fails quickly gets you to a sellable, robust system faster
than trying to design perfection on paper. Inviting the client's input both improves
fit and signals you're on their team, which builds the relationship.

**The moves:**
1. Build the smallest version that runs, and expect it to break.
2. Put it in front of real inputs; collect the edge cases and failure patterns.
3. Turn recurring patterns into guardrails so the system hardens over time.
4. Tell the client early you'll rely on their domain knowledge, and pull them in for
   the judgment calls only they can make.
5. Watch the live system, note when and why it breaks, and fix from evidence.

**Watch out for:** Predictability comes from patterns you can only find by running the
thing — you don't know what you don't know until it fails on real data. Skipping the
client's input risks building something technically sound but wrong for their reality.
